## 可以做什么

AGPL 允许个人、家庭、学校和企业使用、修改及商业使用，也允许收费提供软件或服务。是否需要提供源码取决于协议规定的分发、衍生作品和网络交互条件，不取决于是否盈利。

| 场景 | 标准 AGPL 的主要要求 |
| --- | --- |
| 个人或家庭仅在本机运行、私人修改，不分发也不让其他用户通过网络使用修改版 | 通常不因此要求向公众发布私人修改 |
| 对外提供原软件或修改版的源码副本 | 保留版权、许可及无保证声明，依协议提供受覆盖作品的权利；修改版标注改动及日期 |
| 提供编译包、安装包、容器镜像或私有化交付 | 按协议第4—6条提供受覆盖软件的相应源码，使用协议允许的交付方式；必要时同时提供安装信息 |
| 修改后提供网站、SaaS或API等网络交互服务 | 按第13条，向所有通过网络与修改版交互的用户显著提供免费获取该版本相应源码的机会 |
| 企业内部通过网络让员工使用修改版 | 不能简单按“内部使用”免除第13条；仍需判断是否存在上述网络交互，并向相应用户提供源码获取机会 |
| 合入其他代码形成一个受覆盖的较大程序 | 按第5条等判断整部受覆盖作品的授权及源码范围，不能只公开几份补丁来规避义务 |
| 同一公司其他独立、无关项目，或仅同盘分发的独立软件 | 不因同属一家公司或同一分发介质，就自动受本协议约束 |
| 用户照片、学习记录、生产数据库内容和普通服务密钥 | 不作为业务数据随源码公开，使用模拟资料与配置示例；依法及按协议确有必要提供的安装信息另行判断 |
| 独立第三方库或外部模型服务 | 保留第三方原许可；是否构成受覆盖组合及如何兼容，需按实际集成方式判断 |

“相应源码”（Corresponding Source）包含修改、构建、安装、运行和进一步修改受覆盖作品所需的代码及控制脚本；其具体范围和排除项以第1条等为准。不是“只公开改了哪几行”，也不是“公司所有软件必须公开”。

## 分发与网络服务的实际做法

- 保留 `LICENSE`、`NOTICE`、修改记录及第三方要求保留的声明，不附加禁止商业用途、禁止再分发等额外限制。
- 分发编译包时，根据第6条采用合适的源码交付方式。例如在同一下载入口明确提供对应版本源码的等价访问方式，而不是只链接到可能继续变化的 `main` 分支。
- 发布修改后的网络交互版本时，在用户正常可见的位置提供“源代码”入口，指向实际运行版本的完整相应源码。源码可放在公开仓库或其他满足协议要求的服务器；不能只链接回未修改的上游版本。
- 公开构建说明、必要依赖和配置模板，移除孩子的真实资料、口令、令牌及无关生产数据。不要把“需要提供源码”误解为需要公开所有生产秘密；涉及用户产品安装信息时，应另行核对第6条的具体要求。
- 目前构建包随附 `LICENSE`、`NOTICE`、本说明及直接运行依赖的许可证，但这些文本本身不替代分发者应提供的相应源码。

源码提供给协议要求的接收者或交互用户，不一概等于必须向全世界建立公开仓库；用户取得源码后享有协议赋予的再分发等权利。非商业分发和修改版网络服务同样需要遵守协议。
